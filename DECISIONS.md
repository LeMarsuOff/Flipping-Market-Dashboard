### 2026-03-10 — React prototype started

**Context:** Initial exploration of a dashboard for personal trade journaling. React chosen as a familiar starting point.

**Decision:** Begin with a React prototype.

**Consequence:** Prototype validated the data model and widget concepts but introduced toolchain complexity (bundler, hot reload, npm deps) that felt disproportionate for a single-user tool.

### 2026-03-17 — Pivot React → vanilla HTML/CSS/JS

**Context:** React prototype existed but the build step and component abstraction added friction. The project is maintained by one person with no CI pipeline.

**Decision:** Rewrite as a single-file vanilla JS/CSS/HTML stack — no bundler, no framework, no npm.

**Consequence:** Simpler deployment (open file in browser = done). No build step. Easier for community members to fork and self-host. Codebase now ~50k lines across 3 files (`index.html`, `dashboard.js`, `dashboard.css`). Trade-off: no tree-shaking, no type safety, monolithic files are hard to navigate — mitigated by the function map in `docs/file-map.md`.

### ~2026-04 — BYOT over OAuth as recommended first step for multi-user access

**Context:** Explored opening the dashboard to all Flipping Market community members (~600 users). Full OAuth integration with Notion would require user account management, RGPD compliance review, and Notion integration approval.

**Decision:** Recommend BYOT (Bring Your Own Token) + export/import config as the first step, before committing to full OAuth.

**Consequence:** ~1.5 days dev vs weeks for OAuth. RGPD/Notion review avoided in the short term. Still deferred pending post-Notion-overhaul stabilization.

### ~2026-04 — Raw API trade cache moved in-memory only

**Context:** The raw Notion API response cache was stored in localStorage, causing quota overflow errors (~4.6 MB raw cache exceeded the 5 MB browser limit for some users).

**Decision:** Keep the raw trade cache in-memory only (`appState.trades.items`). Store only `apiFieldNames_v1` (field mapping, small) in localStorage. Trade data is refetched on page refresh via incremental sync.

**Consequence:** No more localStorage quota errors. Cache is lost on page refresh (acceptable — incremental sync is fast). Agents must remember to purge `apiTradesCache_v2_rrmax_*` after structural normalization changes.

### ~2026-04 — Dataset B as primary analysis reference

**Context:** Two datasets were defined: Dataset A (excludes BE-TP/BE-SL trades from all calculations) and Dataset B (includes all outcomes including BE). The dashboard historically used Dataset A as primary for "clean edge analysis."

**Decision:** Dataset B is primary (operational truth). Dataset A is retained as a crosscheck lens available via filter.

**Consequence:** All EV calculations, KPIs, and default filter presets operate on Dataset B. This matches how a live account actually performs — BE trades are real outcomes with real risk. Dataset A analyses are opt-in via the outcome chip filter.

### ~2026-04 — Schema v2 for preset snapshots (unified Filters ↔ Presets)

**Context:** Preset system v1 stored filter state in multiple separate keys (`flipping_preset_overrides`, per-dim arrays on the preset object itself). Adding custom Notion chip support required a unified snapshot format.

**Decision:** Introduce `flipping_preset_snapshots_v2` — a single JSON blob per preset containing all chip state (`chips`, `customChips`, `tpConfig`). Boot-time `_migrateToV2()` silently upgrades v1 data. v1 fields on preset objects are zeroed to prevent drift.

**Consequence:** Cleaner preset isolation. Custom chips and TP config are fully preset-scoped. Breaking this key without a migration silently destroys all user presets — treat as a contract.

### 2026-05-15 — ROBUST-11: two-layer CSS injection hardening in `importTheme`

**Context:** The theme import function (`importTheme`) accepted arbitrary CSS values from a JSON blob (user-controlled or pasted). A malicious or malformed theme could inject `url(https://evil.com)` or `expression(...)` into CSS custom properties.

**Decision:** Add `_isSafeCssValue(val)`: a blacklist check (`url(`, `expression(`, `javascript:`, `data:`) with a 200-char cap. Add a second layer: normalize CSS unicode escapes (`\HH` through `\HHHHHH`) before the blacklist check, preventing bypass via `\75 rl(...)` → `url(...)` at parse time. Fail closed on normalization errors.

**Consequence:** Theme import is now hardened against CSS injection. Values failing the check are dropped with `console.warn`. Legitimate theme values (hex colors, pixel values, font-weight numbers) are unaffected. PR #22.

### 2026-05-17 — Race-guard pattern for async profile-scoped writes

**Context:** `_loadNotionTrades` does a multi-second `await fetch` against the Notion proxy. If the user switches the active journal profile while the fetch is in flight, the response landed in the *new* active profile's cache slot (because `getProfileScopedKey()` reads the live active profile at call time) and `_injectTrades` overwrote the dashboard the user was now looking at. Cache pollution + UI pollution.

**Decision:** Adopt a two-part guard inside every async function that touches profile-scoped state:
1. **Capture the profile context at function entry** — `const profileId = String(profile?.id || '').trim()`.
2. **Pin the cache scope after the await** — set `_journalProfileCacheContextOverride = profileId` so all subsequent `getProfileScopedKey` resolutions go to *the captured profile* regardless of who is currently active. Restore in a `finally` block.
3. **Guard UI side-effects with `stillActive()`** — a helper closure that compares the captured `profileId` against `getActiveJournalProfile()?.id`. UI writes (`_injectTrades`, `setSourceIndicator`, `showDataStatus`, `_updateLastSync`, etc.) only fire when the captured profile is still the active one.

**Consequence:** A's cache always lands in A's slot. B's UI is never overwritten by A's response. Profile meta (`notionTradeCount`, `notionSyncState`) was already safe because `_updateJournalProfileSyncMeta(profileId, ...)` takes an explicit ID. **Apply this pattern** to any future async function that mixes profile-scoped storage writes with UI updates (e.g., `_loadFromAPI`, media queue handlers). The mutex against *concurrent* syncs (two profiles syncing at once) is **not** covered by this pattern — that's a separate deferred issue.

### 2026-05-17 — Demo as virtual data source row (vs. real journal profile)

**Context:** User asked to move the Demo data source from the topbar's mode toggle into the Settings → Data & Integrations data source list, as the first entry. Two paths considered: (A) introduce a new `connectionType: 'demo'` journal profile that synthesizes 100 sample trades, (B) render a virtual non-persisted row at the top of `_renderJournalProfileSwitchList` with a dedicated `setDataSource('demo')` action.

**Decision:** Path B — Demo is **not** a real profile. It's a virtual row injected at render time with `data-profile-id="__demo"` and `data-action="journal-profile-row-switch-demo"`. Adding CSV as a sibling virtual row is tracked in `ROADMAP.md` under "CSV access path after topbar cleanup".

### 2026-05-18 — Local automation layer: spec-in-CLAUDE.md, files gitignored

**Context:** The user works on two machines (Windows + Mac) and is non-technical (does not read code, verifies changes by refreshing localhost). Two recurring frictions were identified: (1) forgetting to bump `?v=N` in `index.html` after editing `dashboard.js`/`dashboard.css` → user refreshes and sees the old cached version, wastes minutes diagnosing; (2) syntax errors slipping through to delivery → user sees a blank/broken dashboard and has to flag it back. Three options for fixing this: (A) commit hook scripts and slash commands to git so both machines share them, (B) keep all local config gitignored under `.claude/` and require per-machine setup, (C) split — keep scripts under `scripts/` (tracked) and only `settings.local.json` (gitignored).

**Decision:** Path B — full per-machine setup, all under `.claude/` (already gitignored). The **spec** for hooks + slash commands lives in `CLAUDE.md` §12 / `AGENTS.md` §12 (committed). On a fresh machine, the user says "install hooks and commands here" and the agent regenerates everything from the spec. Six slash commands are canonical: `/start`, `/end`, `/localhost`, `/status`, `/undo`, `/push`. The hook script is OS-specific (PowerShell on Windows, bash on macOS) — the spec describes the behavior, not the syntax, so each machine gets a native script.

**Consequence:** Local config never collides between machines (no LF/CRLF flame wars, no Mac scripts in a Windows checkout, no permission-mode drift). The price: a one-shot install per machine (~2 minutes). The benefit: the agent on a fresh machine reads CLAUDE.md §12 and rebuilds everything without ambiguity — the spec is sufficient (no git-tracked script source needed). This pattern should generalize to any future per-machine automation (test runners, browser launchers, etc.) — always keep `.claude/` gitignored, always put the spec in CLAUDE.md §12.

### 2026-05-19 — Integrations vs Profiles split: registry pattern, gradual migration

**Context:** Long-term direction is multi-source support beyond Notion: MetaTrader 4/5 (via Expert Advisors), cTrader (Open API OAuth), and potentially Match-Trader / DXtrade / direct broker REST APIs. Today the dashboard's ~30 dispatch sites all branch inline on `profile.connectionType === 'notion'` (else fallback to legacy 'api'). Adding a new source would require finding and editing every one of those sites — high risk of partial migration, easy to miss edge cases. Two surfaces will eventually emerge in the UI: an **Integrations** page (one-time setup per source type) and a **Profiles** page (N profiles per integration, day-to-day switching). The data model split (integrations table + profiles table with FK) is anticipated but not yet implemented; today's `journal_profiles` rows still embed all integration data.

**Decision:** Introduce a runtime registry `INTEGRATIONS[type]` in `dashboard.js` (~line 4625, just after `_renderNotionEditorDbSection`) as the single source of truth for the set of supported / planned data sources. Each entry follows a fixed interface (`id`, `label`, `description`, `icon`, `available`, `isLegacy`, plus methods `isReady(p)`, `getStatusLabel(p)`, `renderEditor()`). Methods are arrow functions so referenced helpers resolve at call time (no hoisting issues across the 27k-line file). A helper `getIntegration(profileOrType)` returns the registry entry, falling back to the `notion` entry for unknown types rather than throwing. Five entries are seeded: `notion` (active, full methods), `api` (active, marked `isLegacy: true`, no UI), `mt5` / `mt4` / `ctrader` (planned, metadata only — `available: false`). The ~30 existing dispatch sites are **not** all migrated at once — only 3 highest-leverage ones in this initial commit (`_renderJournalProfileEditorMarkup` legacy branch + Notion section render, `_getJournalProfilesConnectedCount`, and the connection label at line 27916 area). Remaining sites migrate incrementally (Strangler Fig pattern) as new integrations land or as touched files are revisited for other reasons.

**Consequence:** Adding a fourth or fifth integration (e.g. when MT5 ships) is now bounded: write a new registry entry implementing the interface, no need to chase 30 call sites. The 3 migrated sites already benefit (`_getJournalProfilesConnectedCount` works for any future integration without a code change). Trade-off: until the remaining ~27 sites migrate, the registry is "leaky" — some code still branches inline on `connectionType === 'notion'`, so a new integration would partially work (count + editor + label) but fail at sync/lifecycle paths. The mockup `mockups/integrations-vs-profiles.html` documents the eventual UI target (Integrations page iterates `Object.values(INTEGRATIONS)` showing planned ones as "Coming soon" cards). CSV and Demo are deliberately **not** in the registry — CSV is a one-shot import (no auth, no sync engine) and Demo is a fixed dataset; both stay on their existing code paths until the Integrations page UI is built and we decide whether to model them as pseudo-integrations.

### 2026-05-19 — Ghost-trade reconciliation: 24h auto-trigger + invisible background full sync

**Context:** Notion's incremental sync endpoint (`?last_edited_after=<cursor>`) cannot surface deletions — a deleted page just stops appearing in subsequent responses, with no tombstone, no `_deleted` flag, no signal. The local cache (`apiTradesCache_v2_rrmax_<profile>_<source>`) therefore accumulates "ghost trades" indefinitely: rows the user removed in Notion that keep polluting equity curves, KPIs, and heatmaps. Severity tagged SEV-MED in the 2026-05-17 audit. Three cadence options were considered: (a) full sync on every Sync click — quadruple-digit cost for a deletion that happens once a week at most; (b) manual-only button — discoverability is near zero, 90%+ of community users will never use it and the bug persists; (c) periodic auto-trigger — balanced cost / detection latency, invisible to the user.

**Decision:** Implement option (c) with a 24-hour cadence (`_FULL_SYNC_INTERVAL_MS`). After every successful non-force `_loadNotionTrades` call, `_maybeQueueGhostSyncReconcile(profile, force)` checks `Date.now() - _getLastFullSyncAt() > 24h`; if true, it schedules a follow-up `_loadNotionTrades(profile, { force: true, background: true })` via `setTimeout(0)`. The `setTimeout(0)` defer is load-bearing: it lets the outer call's `finally` block restore `_journalProfileCacheContextOverride` first, otherwise the recursive call would read a stale cache scope after the outer's finally fires post-`await`. The reconcile leverages the existing `force: true` path, which already replaces the cache wholesale (`mergedParsed = parsed` when `fullSync`) — purge is implicit, no separate diff/delete logic needed. A new `background: true` option to `_loadNotionTrades` suppresses every transient UI artifact: no "Loading…" toast, no "syncing…" pill flash, no success toast, no source indicator change, no `_injectTrades` if `purgedCount === 0`. The user sees nothing unless a ghost is actually purged. Power-user escape hatch: a manual "Full resync" item in the profile row's ⋯ menu (`dashboard.js:5252`), gated on `connectionType === 'notion'`, calls `_loadNotionTrades(profile, { force: true })` with normal UI feedback and a completion toast (`N ghost(s) purged · M total` / `complete · M trades · no ghosts` / `failed`). Result communicated to the manual handler via a module-level `_lastFullSyncResult = { purgedCount, tradeCount, ranAt }` sentinel — chosen over modifying `_loadNotionTrades`'s return signature (would touch too many call sites).

**Consequence:** Ghost trades self-purge with at most ~24h latency, fully transparent in the common case. Bandwidth cost: one extra full Notion fetch per user per day (~200–500 trades = ~50–200 KB), each user's own OAuth token (no global rate limit) — negligible at 600-user scale. Edge case: if the user deletes ALL trades in Notion, the empty-trades branch (`dashboard.js:8606`) sets the profile to error state — acceptable, that's a destructive op the user shouldn't accidentally trigger. Concurrent sync mutex still missing (already a TODO Active) — clicking manual "Full resync" while a background reconcile is in flight runs both concurrently; cache writes are profile-scoped so no data loss, just wasted bandwidth. The initial implementation placed the manual button inside `_renderNotionSyncSection` — which turned out to be unreachable dead code (contradictory render gates between `dashboard.js:5267` and `dashboard.js:5136`). Moved to the ⋯ menu in the profile row; the dead-code finding logged as a TODO Active cleanup item.

### 2026-05-20 — Global `localStorage.setItem` dedup wrap (Bloc 4 persistence/refresh investigation)

**Context:** Bloc 4 of the ROADMAP — "identify which localStorage writes are redundant on refresh and whether a debounce strategy is needed." Started by instrumenting `localStorage.setItem` at the very top of `dashboard.js` (gated `?lsAudit=1`) to capture per-key write counts, redundant calls (where the new value matches what's already stored), and payload sizes. Real-usage measurement on Max's 30-second interaction with a 658-trade M15 profile: **230 setItem calls, of which ~152 were exact duplicates of the value already in storage — about 800 KB of fully-redundant writes**. The redundancy was structural, not bursty: `presetLiveFilters_v1_<profile>` fired 28× with 100% identical payloads, `gs_layout_active_<profile>` and `gs_layout_default_<profile>` fired in tandem with identical 13.5 KB payloads on every drag/resize, `flipping_custom_widgets_<profile>` rewrote 22 KB on every heatmap threshold-slider move (due to a `changed = true` bug — see consequence). Targeted fixes per-callsite would have required touching 5-7 unrelated code areas with different ownership patterns. The 122-site grep made it clear a centralized fix was much higher leverage.

**Decision:** Wrap `localStorage.setItem` globally at the very top of `dashboard.js` (before any code runs, even before `DEMO_TRADES`). On every call, compare the proposed value against `localStorage.getItem(key)` — if identical, short-circuit and return without invoking the original setter. Cost is one extra `getItem` per `setItem` call (cheap, no I/O). The audit instrument was kept (still opt-in via `?lsAudit=1`) but merged into the same IIFE — the wrap always dedups; the audit toggle just adds stats tracking on top. Targeted fixes complementary to the wrap (none of these are strictly necessary now that dedup is global, but they avoid wasted CPU on `JSON.stringify` of large payloads): (a) `loadSavedTheme` — only re-writes the merged theme if `JSON.stringify(currentTheme) !== saved`, avoiding a 4.6 KB stringify+write per refresh; (b) sidebar state — unified sync (`_persistSidebarState`) + debounced (`_persistSidebarStateDebounced`) writers through a shared helper `_writeSidebarStateIfChanged` that caches the last payload in memory + compares against localStorage on the first call of the session; (c) `_saveBootSnapshot` — removed the dead `savedAt: Date.now()` field from the payload (only `topbarStatsHtml` is read on boot, per the index.html restore script), so the payload becomes stable when the topbar HTML doesn't change and the dedup wrap catches it; (d) `_commitLinkedSettingsToAllCustomHeatmaps` — replaced the `defs.forEach(def => { changed = true; def.settings = {...} })` bug with a real `prev.metricMode === _sdMetric && prev.threshold === _heatmapThreshold && prev.hardMode === _hmHardMode` short-circuit, which prevents the 22 KB stringify entirely on every heatmap-slider tick. Also added a transitive dedup short-circuit inside `safeSetLocalStorage` itself for defense in depth (most call sites go through it but not all). The `storage` event behavior is unchanged — the browser already only fires it when the value actually changes, so cross-tab listeners are unaffected.

**Consequence:** No call site needs to know about the dedup — it's transparent infrastructure. Future code that writes to localStorage automatically benefits without ceremony. Measured impact on the same 30-second user session, after all fixes: 232 setItem calls → 80 actually reach storage (66% short-circuited), ~444 KB legitimately written + ~800 KB redundancy neutralized. The remaining "true" writes are dominated by GridStack layout persistence (~270 KB across `gs_layout_active` and `gs_layout_<preset>`) and custom widget defs (~107 KB) — both are semantically required state changes, not bugs. **Caveats** logged as deferred TODOs: (i) `gs_layout_active` and `gs_layout_<preset>` write the same 13.5 KB payload to two LS keys on every drag (semantically different: autosave vs per-preset state — global dedup can't help between distinct keys); (ii) ~50% of `gs_layout_*` writes are dedup'd, meaning the GridStack `resizestop dragstop` handler fires even on drags that didn't move anything (snap-back, micro-clicks) — the dedup absorbs the I/O but `JSON.stringify` of 13.5 KB still runs. Both deferred to the next preset/layout architecture pass. The audit instrument stays installed (gated `?lsAudit=1`, zero overhead when disabled) for future investigations — call `__lsAudit({sortBy: "total"|"redundant"|"bytes"})` in the console.

### 2026-05-20 — `/end` branch safety guard + orphan-branch policy (worktree-isolation agents)

**Context:** Audit during the 2026-05-20 session revealed 6 stale `claude/*` branches on the repo (5 with worktrees in `.claude/worktrees/`, 2 on origin) created by agents running in `isolation: "worktree"` mode — cloud agents, ultrareview, and explicit Agent-tool calls with the isolation parameter. Two of those branches carried real unmerged work: `awesome-dubinsky-f03119` (1 doc commit about a prod incident) and `sharp-hoover-38e66d` (the entire Template chooser feature, 7 commits, +375 LOC, never merged for 24+ hours). The risk surface: an isolated agent commits + pushes to its own branch, expects a human to review and merge, but the branch is silently forgotten — meanwhile a future `/end` from the user is harmless because they're on `main`, but a future `/end` from an agent that itself checked out a side branch mid-session (e.g. for testing, then forgot to return) would push to the wrong branch. CLAUDE.md §11 already says "No worktrees. Small tasks → `main` directly." but that rule is enforced by the agent reading CLAUDE.md, not by the harness — and worktree-isolation invocations don't read the project's CLAUDE.md.

**Decision:** Add a defensive step 0 to `/end` (slash command at `.claude/commands/end.md`): run `git branch --show-current`, refuse to proceed if the result is not `main`, surface `git log --oneline main..HEAD` + `git status --short` and ask the user explicitly whether to (a) merge/rebase back onto main before closing, (b) push the side branch as-is, or (c) abort `/end`. Document the same guard in canonical `CLAUDE.md` §12.2 `/end` table cell + `AGENTS.md` mirror, so fresh-machine "install hooks and commands here" regenerates it. Backed by a memory file `feedback_local_commands_customizations.md` as a defensive fallback if spec regeneration misses table-cell nuance. The same `/end` step also folds in step 7 (session rename via `/rename Dashboard - DD/MM - <context>`), which was previously a TODO entry from 2026-05-20.

**Consequence:** From this point forward, `/end` cannot accidentally push the session's commits to a non-main branch on GitHub — the agent stops and asks. Orthogonal complement: the deeper "no worktree" rule in CLAUDE.md §11 stays as-is, since enforcing it would require changing how agents are invoked (a harness-level concern outside CLAUDE.md's reach). Orphan-branch cleanup policy: at the start of any session that touches branch state, the agent should list `git branch -a | grep claude` and surface anything not on main (~3 commands, low cost) — added as soft guidance to future audits. The 6 branches found this session were all eliminated: 4 vacuous (0 ahead of main, just stale HEAD pointers), 2 with content (cherry-picked + merged before deletion). All worktrees in `.claude/worktrees/` removed; the dir is now empty besides the main repo.

### 2026-05-21 — Template detection: pivot schema-based → title-based + Multi-TP as bonus tier + hero-stat / section-counter alignment

**Context:** During real-browser validation of the Template chooser feature (TODO Active "validation pending" from 2026-05-20), four UX bugs surfaced on Max's 6 live Notion profiles. (1) The Data Setup banner displayed the wrong template label ("H4 Pro Template" for an actual H4 Beginner DB): `_detectTemplate(rawTrades)` fingerprinted by inspecting trade VALUES (e.g. `"External Fib Touched"` vs `"Fib - X Touched"`), but Notion's multi_select serialization can vary (array-of-strings vs array-of-`{name}` vs Notion-API-format with `{multi_select: [...]}`) and the option strings themselves shift between template versions — the detection was right at first sync, then locked into the LS via `_setDetectedTemplate(...)`, then drifted out of sync forever. (2) Section bars showed e.g. Optional 11/14 with the 3 `__NO_MAPPING__` dims rendered as is-no-mapping rows behind a footer toggle — Max wanted them gone entirely for template-auto-applied no-mapping (user-set no-mapping should keep the toggle so they can revert). Boot flow inverted: `_reloadJournalProfileSelection` tries `_SW.downloadTradesBlob` BEFORE falling back to `loadFromAPI` Notion fetch — `fromBlobDownload: true` flag passed to `setCachedAPIData` prevents the immediate re-upload loop. ### 2026-05-23 — Raw Notion cache cross-device sync (Task #3.10) — option (b) URL substitution + boot-time hydration + post-bake LS persist

**Context:** Task #3.4 (parsed-trades blob) shipped 2026-05-23 morning solved cross-device propagation of normalized trades and screenshots, but `_rawAPICacheMemory` (the unparsed Notion response used by `_bakeCustomWidgetExtrasIntoCache` for new widget creation and by `_reapplyAPIOverrides` for mapping changes) was left in-memory only. Max reported this regression for 3 consecutive days: refresh → create widget → refresh → widget exists but no data.

**Decision:** Ship the raw blob as a sibling of the parsed blob in the same `notion-trades` bucket — path `<uid>/<profile>_<src>_raw.json.gz`, reusing the gzip helpers and RLS rules. Three sub-decisions tranchées live:

1. **Image URL handling — option (b) with (a) fallback.** Notion S3 signed URLs in File & Media properties expire in ~1 h, so uploading them verbatim would pollute the bucket with dead links that consumers (mapping change re-normalize) would extract on a fresh device. New helper `_substitutePermanentImageUrls(rawTrades, source)` ([dashboard.js:8100](dashboard.js:8100)) walks each trade's screenshot props (resolved via current field overrides), looks up the permanent Supabase URL in the media cache via `(_notionId, slot)`, and substitutes the URL inside the canonical `[{name, file:{url}}]` shape. Orphan trades (no media cache entry — typically <30 s old, before the media queue migrated) get their image props stripped to `[]` rather than left as Notion URLs. Non-image props and external URLs (imgur, cloudinary, TradingView `/x/`) are untouched. Option (c) — upload Notion URLs verbatim — rejected because it pollutes the bucket and breaks the mapping-change-on-fresh-device flow.

2. **Boot hydration as fire-and-forget IIFE** ([dashboard.js:6326](dashboard.js:6326)). Inserted at the top of `_reloadJournalProfileSelection`, BEFORE the LS-cache early-return. Rejected: awaiting the raw blob inside the parsed blob fast-path (would block first paint). Rejected: hoisting raw download into the network fallback branch (skipped when LS cache hits, which is the common case → original regression). Chose: an `(async () => {...})()` block that runs in parallel with the synchronous `_injectTrades` from LS cache. Two guards (pre-fetch + post-await) detect already-populated raw cache and skip the download to avoid clobbering a concurrent Sync's fresher data.

3. **Post-hydration bake catch-up + forced LS persist.** After raw hydration, re-bake every custom widget def (`_loadCustomWidgetDefs` → `for def: _bakeCustomWidgetExtrasIntoCache(def)`), then **explicitly** call `setCachedAPIData(parsedMem, src, { fromBlobDownload: true })`. Loop 1 (`appState.trades.items`) mutates extras in place FIRST, and when both arrays hold the same trade references (the common case after `_injectTrades(cached)` aliases them), Loop 1's mutation makes Loop 2's `hasOwnProperty` check skip → `changed` stays false → bake's internal `setCachedAPIData` is never called → in-memory cache has the new extras but LS does not. On the next hard refresh, LS-derived parsed cache returns empty extras, widget renders empty. The forced LS write closes that gap. This was the root cause of Max's 3-day regression — even with all the cross-device plumbing in place, the bake's `changed`-flag aliasing trap prevented LS from being updated.

**Consequence:** Max's "create widget, refresh, widget has no data" scenario fixed end-to-end. Custom widgets and mapping changes now work on a fresh device without a manual Sync. Acceptable: rare timing, self-heals on next sync. (3) The IIFE runs unconditionally on every Notion-with-DB profile load — one extra Storage GET per device per session. ~30 KB transfer, ~100 ms latency, fine. (4) Custom-widget extras testing required eval-time access to lexical `_customWidgetDefsCache` to bust the boot-cached value — confirmed the bake works correctly when defs are loaded fresh from LS at boot (Max's real-device flow), but the test reproduces required the eval trick. (5) Supabase Realtime push for "PC A → 30 s → PC B updates without F5" still deferred to Session 4. **Cache** JS `?v=562` → `?v=574`.

### 2026-05-24 — Theme editor coverage doctrine : route every color through existing 39 vars, never add new pickers, document 3 design exceptions

**Context:** Max signale "j'aimerais m'assurer que l'intégralité du dashboard puisse être modifiable par rapport aux couleurs — textes, charts, données — mais sans avoir 100 boutons de couleurs différents." Audit Explore initial cartographie 39 vars éditables réparties en 7 groupes (Backgrounds, Borders, Text, Accent & Semantic, States, Chart Palette, Component Overrides) + architecture 3-couches CSS (Layer A foundation → Layer B semantic alias → Layer C composant) + dérivations automatiques dans `applyThemeToCss()` ([dashboard.js:29335](dashboard.js:29335)) qui calculent `--g2`/`--g3`/`--gold2`/`--sel`/`--sel-border` à partir des 13 couleurs foundation. Le système existant est *déjà* bien dimensionné pour le "no 100 buttons" — le problème n'est pas une carence du theme editor, c'est ~60 sites où les couleurs ne le traversent pas (hex en dur dans CSS, rgba en dur dans canvas, alphas blancs/noirs qui assument le dark theme). Au moins une fuite a été trouvée live par Max via screenshot (les tradecards EURUSD affichaient du jaune `rgba(245,200,66,.7)` qui ne suivait jamais le picker `--gold`) — preuve que l'audit ne peut pas tout voir et qu'il faut une doctrine pour décider quoi router et quoi laisser.

**Alternatives considérées:** (1) **Ajouter un nouveau picker par leak (style "Data Type Hints", "Tradecard Values", "Heatmap Text")** — rejeté : viole frontalement le "no 100 buttons" de Max, et chaque nouveau picker est un coût de maintenance + de cognition à perpétuité. (2) **Tout exposer brut, y compris la couche Layer B semantic alias + tous les alphas/gradients** — rejeté : multiplie la surface éditable par ×3 sans gain réel pour l'utilisateur, et l'invariant "foundation cascade vers semantic" disparaît. (3) **Ne rien toucher et accepter que ~60 surfaces drift** — rejeté : ne répond pas à la demande Max, et le drift sur light theme casse l'UX (tradecards qui restent jaune fixe, table row hover invisible, etc.). (4) **Tout router vers les 39 vars existantes via `color-mix(in srgb, var(--X) <pct>%, transparent)` côté CSS et `tcRgba('--X', alpha)` côté canvas, et documenter 3 catégories d'exceptions** — retenu.

**Decision:** **Doctrine adoptée en 4 phases, 59 sites refactorisés, zéro nouveau picker.** **(1) Pattern de routage** : pour les CSS hex en dur, remplacer par `var(--X)` quand le hex match exactement la valeur d'une var existante (cas BE-TP `#2962ff` → `var(--oc-betp)`, BE-SL `#b478f0` → `var(--oc-besl)`, etc.) ou par `color-mix(in srgb, var(--X) <pct>%, transparent)` quand on a besoin d'un tint au lieu d'un opaque (cas `.wd-trade-card-tp` `rgba(110,224,180,.12)` → `color-mix(--g 12%, transparent)`). Pour les canvas RGBA, utiliser le helper existant `tcRgba(varName, alpha)` à [dashboard.js:13464](dashboard.js:13464) (cas equity tooltip bg `rgba(11,18,32,0.88)` → `tcRgba('--bg4', 0.88)`). **(2) Mapping pragmatique** : ne pas créer de nouvelles vars sémantiques — réutiliser les 39 existantes même quand la sémantique n'est pas parfaite (chip "session" teal → `--t`, chip "setup" cobalt → `--b`, chip "pair" violet → `--oc-besl` même si conceptuellement la chip n'est pas BE-SL). Le user qui veut bouger l'accent teal le bouge dans un seul picker et toutes les surfaces "teal" suivent. **(3) Contraste blanc/noir sur bg coloré** : `#fff` sur gold/red bg → `var(--white)` (= main text color, qui adapte light/dark automatiquement et reste lisible sur saturated mid-tone) ; `#000` sur green bg → `var(--text-inverse)` (= flip de la main text, garde le contraste fort). **(4) 3 catégories d'exceptions documentées et explicitement non touchées** : (a) **modal-island UI** — lightbox image viewer (bg `rgba(0,0,0,.88)`, text blanc) + csv-overlay full-page drop zone : ce sont des îlots d'UI intentionnellement dark indépendamment du thème, pattern standard image viewer (cf YouTube, Lightbox.js). Toucher leur palette casserait le pattern user-mental. (b) **theme editor panel internals** (~30 rgba lignes 16485-18883) : le panneau du theme editor lui-même est verre sombre intentionnel, comme les dev tools, pour qu'il reste lisible peu importe ce que l'utilisateur fait avec son thème. Sa palette interne doit *ne pas* suivre le thème par design. (c) **share-view "design canon"** — `.sv-cal-month-daynum-empty` (`rgba(255,255,255,0.16)`), `.is-be` BE dot blanc (`rgba(255,255,255,0.42)`), `.sv-cal-month-trade-pair` text (`rgba(235,242,255,0.86)`) : assumptions dark-theme intentionnelles dans le PNG export. Les bouger affecterait la canonicité du share-view PNG cross-machine (un user thème clair génère un screenshot différent d'un user thème dark). À discuter séparément si Max veut casser cette consistance. **(5) Validation systématique** : à chaque phase, probe en preview via `getComputedStyle` sur des éléments cibles + mutation live `document.documentElement.style.setProperty('--X', '#ff00ff')` pour prouver que la surface suit le picker en temps réel.

**Consequence:** **(A)** L'intégralité du dashboard (hors les 3 exceptions documentées) répond maintenant aux 39 pickers existants. Tradecards, mobile trade log, badges required, lt-active dot, htf-toggle, chip hovers par catégorie, tooltips BE-TP/BE-SL, topbar separators, equity tooltip, calendar empty days, share-view crosshair, etc. — tout cascadent depuis `--g`/`--r`/`--gold`/`--b`/`--t`/`--oc-betp`/`--oc-besl`/`--white`/`--text-inverse`/`--bg4`/`--dim`/`--streak-orange`/`--streak-purple`. **(B)** Le nombre de vars éditables ne change pas (toujours 39), les 7 groupes du theme editor restent intacts, aucune migration LS nécessaire. **(C)** Le helper `color-mix(in srgb, var(--X) <pct>%, transparent)` côté CSS et `tcRgba('--X', alpha)` côté canvas devient le **pattern canonique** à utiliser pour toute nouvelle surface couleur (à ajouter dans CLAUDE.md §7 lors de la prochaine revue conventions). **(D)** Les 3 catégories d'exceptions ont une raison documentée — si Max ou un futur agent veut les "fixer", il faut d'abord lire cette decision pour comprendre pourquoi elles sont volontaires. **(E)** Limite résiduelle : l'audit Explore initial avait raté `.wd-trade-meta-value` (les valeurs jaunes des tradecards visibles dans le drawer), trouvé live par Max via screenshot. Confirme que les agents Explore ont des angles morts sur les CSS classes non-canoniques (`.wd-` prefix vs grep large) — le 2e scan ciblé (drawer + tradecards + log panel + custom widgets) a trouvé 17 leaks de plus en Phase 4. Pour la prochaine surface UI, refaire un grep complet `#[0-9a-f]{6}` + `rgba\([0-9]` après ajout, et systématiquement passer par les vars existantes dès la première écriture (pas a posteriori). Cache CSS `?v=250 → 271`, JS `?v=711 → 725`.

### 2026-05-25 — Realtime Push Phase 0 : optimistic-concurrency RPCs + watcher table + publication

**Context:** Bug réel rapporté par Max le 2026-05-25 : PC A fait des modifs (presets, layout, etc.) → 2h plus tard PC B (dont la fenêtre était restée ouverte tout ce temps avec un état in-memory figé) déclenche un autosave → écrit son blob stale par-dessus le blob frais de PC A → Max perd irrécupérablement les modifs PC A. Audit du pipeline Supabase ([dashboard.js:566](dashboard.js:566) `_SW.set` via monkey-patch `localStorage.setItem`, [dashboard.js:1071](dashboard.js:1071) `saveJournalProfilesToRemote`, [dashboard.js:768](dashboard.js:768) `uploadTradesBlob`) : **aucun version-check au write**. Toutes les écritures sont LWW direct upsert. Realtime n'était pas non plus activé → PC B ne saurait jamais que PC A a poussé. L'objectif est **zéro perte de saves**, validé explicitement par Max (vs alternatives "LWW + toast" ou "modal manuelle"). L'audit montre que Realtime SEUL ne suffit pas — il faut aussi bloquer les écritures stale au niveau DB, sinon entre le moment où PC B reçoit l'event et le moment où il décide de re-pull, n'importe quel autosave peut clobberer.

**Alternatives considérées:** (1) **LWW + Realtime + toast "Synced from another device"** — rejeté : Max veut zéro perte, pas "perdez le moins souvent possible". (2) **Modal bloquante "Resolve manually"** avec les deux versions côte-à-côte — rejeté : lourd à coder pour toutes les surfaces de save (preset, layout, theme, mappings, custom widgets, trades). (3) **Ajouter une colonne `version BIGINT` aux 3 tables + trigger qui incrémente** — rejeté : redondant avec `updated_at` qui existe déjà sur les 3 tables. (4) **Utiliser `updated_at` comme version-clock + trigger `BEFORE UPDATE` qui set `NEW.updated_at = now()` automatiquement + RPCs SECURITY DEFINER qui RAISE 'stale_write' quand `existing.updated_at > seen`** — retenu. (5) **Pour le Storage blob trades** : pas de Realtime natif → soit (a) re-écrire les trades en table Postgres (rejeté : ~6-30 MB/user dépasse les ergonomies), soit (b) ajouter une table watcher légère `trades_blob_meta(user_id, profile_id, source, updated_at, blob_size)` qu'on bump atomiquement à chaque upload Storage — retenu.

**Decision:** **Phase 0 = migrations DB only (aucun code client touché).** Quatre migrations appliquées via MCP Supabase, toutes additives, toutes rollback-able via `DROP`. **(M1) `auto_bump_updated_at_triggers`** : fonction `set_updated_at_now()` + 3 triggers `BEFORE UPDATE` sur `user_data`, `journal_profiles`, `notion_connections`. Sans ces triggers, le `default now()` sur `updated_at` ne se réapplique qu'à l'INSERT — un UPDATE laisse `updated_at` figé et le version-check serait inopérant. **(M2) `stale_write_check_rpcs`** : 4 RPCs `SECURITY DEFINER` avec `search_path = public` pinné et `GRANT EXECUTE TO authenticated` uniquement : `upsert_user_data_if_unchanged(p_dashboard_id, p_key, p_value, p_seen_updated_at)`, `delete_user_data_if_unchanged(...)`, `upsert_journal_profile_if_unchanged(p_id, p_row jsonb, p_seen_updated_at)`, `delete_journal_profile_if_unchanged(...)`. Chacune fait un `SELECT updated_at` pour la row cible, compare avec `p_seen_updated_at`, et `RAISE EXCEPTION 'stale_write' USING ERRCODE = 'P0001', HINT = v_current::text` si remote > seen. Sinon upsert/delete et `RETURN` le nouveau `updated_at`. Le `HINT` permet au client de récupérer la version actuelle sans une round-trip SELECT supplémentaire. **(M3) `trades_blob_meta_watcher_table`** : nouvelle table `(user_id uuid, profile_id text, source text, blob_size bigint, updated_at timestamptz, PK (user_id, profile_id, source))` avec RLS activée (policies SELECT/DELETE pour `auth.uid() = user_id`, INSERT/UPDATE bloqués pour direct access — passent uniquement par la RPC `bump_trades_blob_meta` SECURITY DEFINER). Trigger `BEFORE UPDATE` auto-bump `updated_at`. **(M4) `enable_realtime_publication`** : ajoute les 4 tables (`user_data`, `journal_profiles`, `notion_connections`, `trades_blob_meta`) à la publication `supabase_realtime` (Postgres logical replication) pour permettre aux clients de subscribe via `postgres_changes` à la Phase 2. Idempotent — utilise `DO $$ ... EXCEPTION WHEN duplicate_object THEN NULL`. **(M5) Hardening** : `harden_rpc_security` corrige 2 advisor warnings — `set_updated_at_now` gagne son `SET search_path = public` qui manquait + `REVOKE EXECUTE ... FROM PUBLIC, anon` sur les 5 RPCs (le `auth.uid() IS NULL → RAISE not_authenticated` est défensif côté code, mais lock au GRANT layer = ceinture + bretelles).

**Consequence:** **(A)** Backend prêt pour les Phases 1-3. Aucun code client touché → l'app continue de fonctionner à l'identique tant que les writes ne passent pas par les nouvelles RPCs. Backward-compat parfaite. **(B)** Pattern `expected_updated_at + RPC qui RAISE 'stale_write'` devient le canon pour tout nouveau write côté client. À la Phase 1, `_SW.set/_SW.remove/saveJournalProfilesToRemote/uploadTradesBlob` seront wrappés pour : (i) maintenir un cache `_lastSeenUpdatedAt[key]`, (ii) appeler la RPC avec `expected_updated_at`, (iii) sur exception `P0001` re-pull la row + retry une fois. **(C)** Watcher table = pattern explicite pour ajouter Realtime à n'importe quelle ressource Storage future (notion-screenshots, etc.) : on bump une row au upload, les clients subscribed savent. **(D)** Coût latence write : +50-100ms par save (1 round-trip RPC au lieu d'un direct upsert PostgREST). Négligeable vs la valeur "jamais perdre de saves". **(E)** Risque résiduel à la Phase 1 : un client ancien (avant déploiement Phase 1) qui écrit direct via PostgREST `upsert` continuerait à clobberer. Mais à ce stade, seul Max utilise l'auth Supabase (les 600 community sont en demo/Notion direct sans Supabase login) → pas de risque externe, juste un hard-refresh requis après le déploiement Phase 1. **(F)** Aucun fichier code touché dans ce commit → traçabilité 100% via DECISIONS + ROADMAP + le snapshot des migrations appliquées (accessible via `mcp__supabase__list_migrations`). **(G)** Les advisors Supabase sont propres pour ce qui touche cette migration ; les 2 warnings restants (`notion_media_cache` RLS sans policy, `auth_leaked_password_protection`) sont préexistants et orthogonaux. Le warning `authenticated_security_definer_function_executable` × 5 est by design (on VEUT que les users signed-in puissent appeler ces RPCs — c'est leur raison d'être).

### 2026-05-25 — Realtime Push Phases 1-3 : client wrapper, Realtime sub, refocus + reconnect

**Context:** Suite de la Phase 0 (migrations DB shippées commit `76c8231`). Trois phases code client pour : (1) refuser les writes stale au niveau DB via les RPCs `*_if_unchanged` de Phase 0, (2) propager les changements cross-device en live via Supabase Realtime postgres_changes, (3) refaire un full pull au refocus tab + reconnect WS. Le bug Max du 2026-05-25 = PC B (tab ouvert 2h, in-memory state figé) clobbere le blob Storage de PC A au prochain autosave → données irrécupérables. Phase 1 est la pièce load-bearing (stale-check au write empêche le clobber) ; Phases 2-3 sont l'UX magique ("PC A → 30s → PC B updates sans F5").

**Alternatives considérées:** déjà couvertes dans la décision Phase 0 supra (LWW+toast rejeté, modal manuelle rejetée, ajout colonne `version` rejeté). Pour les Phases 2-3 spécifiquement : (1) **subscribe BEFORE initial pull** — rejeté : race possible où un event arrive avant que le seen-cache soit hydraté, set l'ancienne valeur. (2) **disconnect WS sur visibilitychange hidden + reconnect sur visible** — rejeté : coût de reconnect (~500ms) chaque fois que l'user switch d'onglet, inutile dans 99% des cas (<10s). (3) **Force re-pull à chaque event** au lieu de write-through + dispatch — rejeté : N events = N re-pulls, gaspille bande passante. (4) **Self-event mute via ETag/timestamp returned by RPC + 5s TTL set** — retenu : pas de migration de schéma supplémentaire, robust to clock skew, TTL court borne le coût mémoire.

**Decision:** **Architecture en 3 couches, déployées séquentiellement avec commit/push entre chaque.**

**Phase 1 — Optimistic-concurrency wrapper côté client** (commit `a124ec1`, +384/-59 lignes). Nouveau state dans le closure `_SW` à [dashboard.js:408](dashboard.js:408) : `_lastSeenUpdatedAt` (Map keyed par `ud|<dashId>|<key>` / `jp|<id>` / `blob|<profileId>|<source>`) + `_selfWrites` (Map des `(table|composite|updated_at)` qu'on vient d'écrire, TTL 5s). Quatre surfaces wrappées : (a) `_SW.set/_SW.remove` ([dashboard.js:594](dashboard.js:594)) appellent `upsert_user_data_if_unchanged` / `delete_user_data_if_unchanged` avec `p_seen_updated_at` lu depuis le seen-cache. Sur exception P0001 → re-pull la row → retry une fois → si encore stale, toast `"Sync conflict — refreshed from cloud"` + adopter remote local. (b) `migrateProfileScopedKeys` ([dashboard.js:752](dashboard.js:752)) reconcile path utilise le même RPC pour cohérence du seen-cache. (c) `saveJournalProfilesToRemote` ([dashboard.js:1160](dashboard.js:1160)) passe d'un bulk upsert à per-row RPC via `Promise.allSettled` : chaque profil porte son propre `p_seen_updated_at`, un stale sur une row n'abort pas le batch. Cleanup DELETE des orphans reste bulk (pas de concurrent edit à protéger). (d) `uploadTradesBlob` + `uploadRawTradesBlob` ([dashboard.js:894](dashboard.js:894) / [979](dashboard.js:979)) bump la watcher meta FIRST via `bump_trades_blob_meta` (stale-checked), THEN upload Storage. Order important : si bump fail (stale), Storage n'est jamais touché → blob frais cloud préservé. Le raw blob utilise watcher source `m15_raw`/`h4_raw` (row distincte du parsed). Read-side : `syncFromRemote` + `loadJournalProfilesFromRemote` + `downloadTradesBlob`/`downloadRawTradesBlob` populate `_lastSeenUpdatedAt` à chaque pull. Hooks exposés pour Phase 2 : `_SW._isSelfWrite/_setSeen/_getSeen/_deleteSeen/_seenKey/getClient`.

**Phase 2 — Supabase Realtime cross-device live sync** (commit `421d5fd`, +198/-1 lignes). Nouveau module top-level `_swRealtime` à [dashboard.js:1490](dashboard.js:1490) après `window._SW = _SW;`. Subscribe à `postgres_changes` sur les 4 tables filtrées par `user_id=eq.<own>`. Quatre handlers : (a) `_onUserData` write-through à LS via le helper `_lsSetUntracked` (exposé depuis le monkey-patch IIFE à [dashboard.js:1617](dashboard.js:1617)) pour éviter re-firer `_SW.set` en loop infinie, update seen-cache, dispatch `CustomEvent('rt:user_data')`. (b) `_onJournalProfiles` update seen + appelle `hydrateJournalProfilesFromRemote` pour réutiliser le pipeline de merge + render existant. (c) `_onNotionConnections` re-check badge intégration Notion. (d) `_onTradesBlobMeta` update seen + ONLY pour le profil actif ET source `m15`/`h4` (skip raw), appelle `_reloadJournalProfileSelection({})` qui re-download le blob + re-inject les trades. **Self-event mute** : chaque write réussi appelle `_markSelfWrite(table, composite, returnedUpdatedAt)`. À la réception d'un event, si `_SW._isSelfWrite(table, composite, payload.new.updated_at)` → skip (sinon double-render + risque d'autosave loop). Toast `"Synced from another device"` throttle 10s (réutilise `_showToast` existant). Lifecycle hooks dans `onAuthStateChange` du `_SW` closure : `connect()` sur `SIGNED_IN` (après `syncFromRemote` complete pour que le seen-cache soit hydraté), `INITIAL_SESSION`, et la fallback `getSession()` Safari ITP. `disconnect()` sur `SIGNED_OUT` pour tear down la WS. Idempotent : connect skip si déjà subscribé pour ce uid.

**Phase 3 — Refocus + WS reconnect force-pull** (commit `924034f`, +73/-2 lignes). Extension de `_swRealtime` : helper `_forcePull(reason)` qui run `syncFromRemote` → `hydrateJournalProfilesFromRemote` → `_reloadJournalProfileSelection({})` en séquence, debounced via `_pullInFlight` pour éviter double-pull si refocus + reconnect tirent back-to-back. Deux déclencheurs : (a) `visibilitychange` listener registered une fois au module init (survit signOut/signIn cycles). Sur `hidden` → record `_hiddenSince = Date.now()`. Sur `visible` → si `(Date.now() - _hiddenSince) > 10000ms` AND user signed-in → `_forcePull('refocus')`. Sous 10s = brief tab switch, no-op. (b) `channel.subscribe()` status callback détecte les reconnects. La première `SUBSCRIBED` après `connect()` est l'initial ; les `SUBSCRIBED` subséquentes sont des auto-reconnects après `CHANNEL_ERROR`/`CLOSED`/`TIMED_OUT` → `_forcePull('WS reconnect')`. La méthode publique `_swRealtime.forcePull(reason)` est exposée pour usage manuel/debug.

**Consequence:** **(A)** Le bug Max est **structurellement impossible** : PC B's stale tab → tente d'upload Storage → bump_trades_blob_meta RPC compare current vs seen → `RAISE stale_write` → Storage jamais touché → blob frais cloud intact. PC B re-pull au prochain Realtime event ou refocus. **(B)** UX cross-device "magique" : PC A modifie un preset → PC B's tab voit l'event postgres_changes dans <2s → re-render + toast `"Synced from another device"`. Pour les trades blob, PC B re-télécharge automatiquement quand l'event meta arrive. **(C)** Tab kept hidden 2h+ → `visibilitychange visible` après >10s hidden → `_forcePull` recharge tout. Couvre le cas exact que Max a vécu. **(D)** Self-event mute = TTL 5s sur la Map `_selfWrites`. Robust to network jitter mais borne le coût mémoire (max ~quelques centaines d'entries). **(E)** Coût WS : 1 connection par tab ouvert, free tier Supabase couvre largement. ### 2026-05-26 — Share links: snapshot architecture + public-by-ID RLS pattern

**Context:** Max veut un bouton "Share" dans la drawer de drilldown qui génère un lien public 7-jours pointant vers la liste de trade-cards d'un chip donné (ex: "Contre Order Flow" → 48 trades + screenshots), partageable à la communauté (~600 membres) sans exposer le reste du dashboard. Trois sous-décisions architecturales se posent : (1) que stocker côté backend — snapshot complet ou référence vers la donnée live ; (2) où le viewer tourne — page autonome ou variante du dashboard ; (3) comment gérer l'accès anonyme — auth requise, magic link, ou public-by-ID.

**Alternatives considérées:**
**(a) Référence + live query** — stocker juste `{filter_chips, journal_profile_id}` sur la table `shares` ; le viewer query la donnée live de Max via Supabase à chaque load. **Rejeté** : (i) couple le viewer à la disponibilité/sync de Max (si Max disconnect son Notion, le lien casse) ; (ii) un trade supprimé/édité dans Notion change rétroactivement le contenu du share (Max partage "+43.8R", la communauté ouvre 3j plus tard et voit "+38.2R" parce qu'un trade a été reclassé) ; (iii) requires que le RLS du viewer puisse lire la trade-data de Max — soit on duplique policy pour viewer-by-id (complexe), soit on fait un endpoint security-definer qui retourne les trades filtrés (sécurité fragile, fuite potentielle du filtre).
**(b) Snapshot immutable** — sérialiser au moment du Share l'array complet de trades filtrés + stats + URLs media dans une row jsonb. **Retenu** : (i) self-contained, aucun couplage live ; (ii) reproductible — la communauté voit exactement ce que Max a vu au moment du clic ; (iii) RLS triviale (public read by ID, expire_at > now()) ; (iv) léger en stockage (~150 KB pour 100 trades, jsonb compressé côté Postgres) ; (v) trade-off accepté = le snapshot ne reflète pas les corrections post-share, mais ça correspond exactement à l'usage attendu (= partager un état à un instant donné, pas un live feed).
**(c) Page viewer = variante du dashboard avec mode "shared"** — réutiliser `index.html` + `dashboard.js` mais cacher tout sauf la drawer via un flag URL `?shared=<id>`. **Rejeté** : (i) un bug de "hide" laisse fuiter du code métier ou des données (filtres, mappings, calcs internes) à la communauté ; (ii) `dashboard.js` est 44k lignes — payload énorme pour afficher 1 drawer ; (iii) coupling fort entre share-mode et dashboard-mode rend tout changement futur risqué (chaque refactor doit re-vérifier que le share-mode ne fuite pas).
**(d) Page viewer standalone (`share.html`)** — fichier autonome qui charge uniquement Supabase JS + un mini renderer trade-card forké du mockup. Aucune dépendance à `dashboard.js` / `dashboard.css`. **Retenu** : (i) surface d'attaque minimale — le viewer ne CONNAÎT pas le dashboard, donc ne peut pas le fuiter ; (ii) déployable en parallèle (changements dashboard ne bougent pas le viewer et vice-versa) ; (iii) payload léger (~50 KB JS+CSS+HTML pour rendre N cards) ; (iv) trade-off = duplication code de rendu trade-card, acceptable car le rendu est simple et stable.
**(e) Auth requise côté viewer** — la communauté doit créer un compte pour ouvrir le lien. **Rejeté** : kills l'use case "drop link in Discord and discuss", augmente friction massivement pour 600 membres sans valeur ajoutée (la donnée est déjà publique de facto via les screenshots Supabase media URLs accessibles par CDN). Pas de PII à protéger.
**(f) Magic link à usage unique** — chaque ouverture invalide le lien. **Rejeté** : friction pour re-partager au sein d'un thread Discord, et le user a explicitement dit "ça ne me dérange pas que tout le monde puisse y accéder, c'est même le but". Le modèle correspondant = unlisted YouTube / Loom unlisted = le lien EST le secret.
**(g) Public RLS read by ID + security-definer RPC pour view_count** — `SELECT` ouvert à `anon` tant que `expires_at > now()`, et un RPC `increment_share_view(id)` security-definer pour bumper le compteur côté anonyme. **Retenu** : (i) deux primitives Postgres standard, aucune edge function nécessaire ; (ii) RLS supervise l'expiration server-side (un lien expiré ne fuite jamais ses données, peu importe le client) ; (iii) le RPC isolé ne peut faire qu'UNE chose (bump view_count by 1 sur une row matchée par ID), donc même si abusé en masse l'impact est borné à inflate un compteur (cosmétique).

**Decision:**
**(A) Snapshot architecture** — alternative (b). Table `public.shares` avec `trades jsonb` (array complet), `stats jsonb` (pré-calculé), `chip_name + chip_kind` (pour le watermark). Aucun couplage à la donnée live de Max. Snapshot immutable (pas de policy `UPDATE`).
**(B) Standalone viewer page** — alternative (d). Phase 3 livrera `share.html` + `share.css` + `share.js` indépendants du dashboard, chargeant uniquement `@supabase/supabase-js` via CDN.
**(C) Public-by-ID RLS pattern** — alternative (e) + (g). `SELECT` policy `USING (expires_at > now())` ouvert à `anon`. RPC `increment_share_view(p_share_id)` security definer, `grant execute to anon, authenticated`. Linter flag `anon_security_definer_function_executable` documenté comme intentionnel dans `docs/share-link-feature.md §4`.

**Consequence:**
**(A)** Nouveau pattern canonique pour les features de "partage public d'un sous-ensemble de données utilisateur" : snapshot immutable + standalone viewer + RLS public-by-ID. À reprendre tel quel si on partage un jour une equity curve, un PNL calendar, ou une stats card. **(B)** Stockage : ~150 KB par share moyen × 1000 shares = ~150 MB → bien dans free tier Supabase (500 MB). Réévaluer si volume × 10. **(C)** `pg_cron` non installé sur le projet — le purge weekly du backlog d'expirés n'est pas actif. Pas urgent : la RLS rend les rows expirées invisibles dès `now()`, donc c'est juste du garbage en attente. Installer l'extension via dashboard Supabase quand le volume justifie. **(D)** Phase 1 (cette session) = backend + spec uniquement. Phases 2 (source button) et 3 (viewer page) restent à livrer dans des sessions séparées — chaque phase est self-contained et testable indépendamment. **(E)** Trade-off accepté : un trade modifié dans Notion après création du share NE met PAS à jour le contenu du share. C'est attendu (le share = état à un instant T), pas un bug. Documenté dans `docs/share-link-feature.md §2` (invariant n°1). **(F)** Limitation actuelle : le viewer dépend de la disponibilité du CDN Supabase pour les médias (URLs `permanent_url` de `notion_media_cache`). Si Supabase a un outage, les screenshots ne loadent pas mais les cards textuelles continuent. Acceptable.

### 2026-05-30 — Classifier functions must reject non-object cfg arguments

**Context:** The Rolling Win Rate overlay (and 11 other sites) call the trade classifiers as bare array callbacks: `arr.filter(isWinner)`. `Array.prototype.filter` invokes the callback as `(element, index, array)`, so `isWinner(trade, index)` received the loop index as its optional `cfg` (tpConfig) parameter. The old guard `cfg = cfg || appState.ui.tpConfig` accepted any truthy value, so a numeric index (1, 2, 3…) flowed through: `_hashTpConfig(number)` returned `"undefined|be:…"` (cache miss) and `computeEffectiveRR(trade, number)` hit the `switch default` → `return trade.r` (raw journaled R). Result: every element past index 0 in each window was classified by the raw outcome instead of the effective-R under the active plan. Invisible in Fixed mode (raw == effective there); only surfaced in Multi/Custom, where e.g. a BE-SL with a captured partial is +R effective but −1R raw.

**Decision:** Added `_normTpCfgArg(cfg)` = `(cfg && typeof cfg === 'object') ? cfg : appState.ui.tpConfig`, used by `isWinner` / `isLoser` / `isBE`. Any non-object `cfg` (notably an array index) is ignored and the function falls back to the active config. Fixed at the function level rather than patching the ~12 call sites, since the footgun is intrinsic to passing these functions as `.filter`/`.map` callbacks and any future call site would reintroduce it.

**Consequence:** All classifier call sites are now safe whether invoked as `arr.filter(isWinner)` or `isWinner(t, presetCfg)`. The only legitimate `cfg` is a tpConfig object, so the type guard is strictly safer than the previous truthiness check with zero behavioral change for valid calls. Rule going forward: the second arg of `is*`/`computeEffectiveRR` is a config object only — never thread anything else through, and never assume `.filter(isWinner)` passes only the element.

### 2026-05-31 — "Break Even" directionless outcome: always-0R, plain-BE-only in the tile

**Context:** Traders whose Notion "Position Result" only has a flat "BE" value (not split into BE-TP / BE-SL) had no dedicated mapping line — mapping it to "Other" excluded the trade from every widget. ### 2026-05-31 — Mapping-config keys are exempt from the apply-remote echo-guard drop

**Context:** A community member reported that Mapping settings (RR Max + screenshot links) kept reverting to the template default — on refresh and sometimes "on its own" mid-session. Root cause was three interacting sync defects: (1) `syncFromRemote` + `_onUserData` apply remote mapping values with unconditional "remote wins" (no local-newer check); (2) the `localStorage.setItem` monkey-patch silently SKIPS `_SW.set` for ALL writes while the `_isApplyingRemote` echo-guard window (1.5s) is open — so a pencil-pick made in that window stayed local-only and never reached Supabase; (3) the reconcile pass only pushes keys MISSING from remote, so a present-but-stale cloud row is never repaired. Net: the cloud stayed pinned to the first-sync template default, and every remote-wins pull restored it over the user's local customization.

**Decision:** Exempt mapping-config keys (`apiFieldOverrides_v1_*` / `apiFieldNames_v1_*`, `_h4` variants included, via new helper `_isMappingConfigKey`) from the blanket echo-guard drop. During the apply-remote window these writes are QUEUED into `_pendingSyncWrites` instead of dropped; the `_enterApplyingRemote` timer drains the queue via `_flushPendingSyncWrites` (which bypasses the monkey-patch) when the window closes. Preset/theme/layout keys keep the drop behavior unchanged. Defect 3 (reconcile re-pushing stale-but-present rows) was deliberately NOT fixed this session — tracked as a separate Active TODO because it raises a local-vs-cloud "who wins" question that can conflict in other cross-device scenarios.

**Consequence:** Mapping saves now always reach the cloud, which makes the unconditional remote-wins pull harmless. The exemption is safe from the echo-loop the guard protects against because `_onUserData` does NOT trigger a re-render cascade for mapping keys (only presets/themes do), so a queued mapping upload cannot ping-pong. Rule going forward: the echo-guard drop is only correct for keys whose `_onUserData` handler re-renders (and thus re-writes LS); any user-config key that is NOT part of a re-render cascade should be queued-not-dropped during the window. Members whose cloud row is already corrupted must re-enter the mapping once after deploy (until defect 3 is addressed) — the local value then overwrites the stale cloud default and persists.

### 2026-06-01 — Auto-template-mapping never re-seeds defaults on an already-synced profile

**Context:** After the 2026-05-31 cross-device sync fix, a member still hit the "mapping reverts to default" bug — this time on a profile RE-SYNC. ### 2026-06-09 — Share-link rich previews (Discord/Slack/Twitter) via Supabase image + standalone Vercel SSR

### 2026-06-11 — Preset id space bounded to [0, PRESET_MAX) with id recycling (reverses "ids never recycled")

**Context:** Max reported an intermittent bug — duplicating an existing preset via the Filters split-button "Save as new preset" produced a *blank* preset (filters not copied), while creating a blank preset worked. Investigation (reproduced deterministically in preview) showed the root cause was NOT in the duplication logic (`savePresetFromLive` builds the snapshot correctly in memory) but in the persistence layer. The old `_nextPresetId()` returned `max(existing id) + 1`, and a prior design comment asserted "ids are stable and never recycled". But the entire preset persistence subsystem is keyed on the range `[0, PRESET_MAX)` (=0..9): `savePresetSnapshots`/`savePresetOverrides` loop `id < PRESET_MAX`; `loadPresetSnapshots`/`loadPresetOverrides` skip `id >= PRESET_MAX`. After enough create/delete churn (ids never recycled), `_nextPresetId` could return an id ≥ PRESET_MAX (e.g. fill 0..9, delete one, create → id 10). A preset with id ≥ 10 had its snapshot **silently dropped on save** — it rendered fine in memory for a moment, then reverted to blank on the next reload or cross-device sync pull. The "never recycled" invariant was therefore incompatible with the bounded persistence it claimed to protect.

**Decision:** Invert the invariant. `_nextPresetId()` now returns the **lowest free id in [0, PRESET_MAX)** instead of `maxId+1`, guaranteeing every allocated id stays inside the range the persistence layer can serialize. ID recycling is safe because `deletePreset()` already wipes a deleted slot's snapshot (→ `_blankSnapshot()`), override (→ neutral) and live slot (→ deleted) — so a recycled id never inherits stale state. `createPreset`/`savePresetFromLive` additionally reset the slot before use (defensive). Scope kept minimal: only the allocator changed; the bounded save/load loops were left as-is (they are correct *given* in-range ids). A separate optional boot migration to remap presets *already* stuck at id ≥ PRESET_MAX (whose snapshot is already lost) was proposed to Max but **not** taken this session — the reporter's own presets are all in-range (0..9), so the allocator fix fully resolves his case; the migration is tracked as a TODO Active pending his go-ahead (it's more sensitive — it touches ids + active-id persistence + compare dropdowns).

**Consequence:** Preset ids are now a bounded, recycled resource (max PRESET_MAX live at once, ids 0..PRESET_MAX-1). Any future code must NOT assume preset ids are monotonic or creation-ordered — `order` (not `id`) is the display-sequence field, and `_getPresetDisplayNum` already decouples the two. The stale design comment was replaced. The same root-cause pattern (a persistence loop bounded by a max that the id allocator could exceed) is worth checking if any other id-keyed store is added.

### 2026-06-11 — Partial Optimizer slots: keep per-preset scope, force-sync the save to cloud

**Context:** Max reported PO saved slots (P1/P2/P3) not surviving across sessions or profiles when signed in. The slots live in `presetLiveFilters_v1` (scoped per dashboard-preset AND per profile by design — a PO preset is just model params, recomputed against current data). Demo-mode (signed out) persistence works fine. The loss only happened signed-in and intermittently. Root cause: the `localStorage.setItem` monkey-patch drops any non-mapping write that lands inside the ~1.5s "apply-remote" window (re-armed on every inbound Realtime preset/theme/blob event) to prevent an echo loop. A PO-slot save coinciding with that window never reached Supabase → lost cross-device, then a stale remote-wins pull overwrote the local slot too. Same class as the 2026-05-31 mapping-config drop bug. Decision point raised with Max (AskUserQuestion): should PO presets become global (across profiles/presets) or stay per-preset with just the sync fixed? Max chose: **keep per-preset scope, fix the sync** (and clarified "replace the button" was a misspeak for "repair the button").

The pattern "user-initiated write to a sync key that's otherwise window-dropped → force-push via `_SW.set` right after the LS write" is now established (mapping force-flush + this) and should be the template for any future deliberate-user-action write to a synced key that isn't a mapping-config key. ### 2026-07-03 — Supersession tokens for concurrent profile switches (kill the "M15 shows H4 data" race)

**Context:** A latent, non-reproducible bug (diagnostic-instrumented 2026-05-20, dormant in memory since): switching journal profiles sometimes showed another profile's trades ("sur profil M15 il m'affiche la data du profil H4"). The trade cache is scoped by `apiTradesCache_v2_rrmax_<profileId>_<htf>`, where `profileId` resolves through the module-global `_journalProfileCacheContextOverride`. The full-fetch path (`_loadNotionTrades`) was hardened 2026-05-22 (per-profile mutex + post-await re-pin), but the **common** switch/boot path — `_reloadJournalProfileSelection` doing `await _SW.downloadTradesBlob(...)` then `setCachedAPIData` + `_injectTrades` — had **no supersession guard and no post-await re-pin**. The insidious trigger needs no rapid clicking: the **Realtime blob-echo** (`dashboard.js` ~1842) fires `_reloadJournalProfileSelection({})` from another device's sync; if the user switches profiles during that network await, the echo steals the override and writes/injects its profile's trades into the newly-active profile's slot/view. The diagnostic missed it because `_injectTrades` tagged `__diagSourceProfileId` with the *current-active* profile (which matched). Compounding: `_applyActiveJournalProfile`'s `finally` restored a `previousOverride` captured at a transient-overlap instant, leaving the override pinned to the wrong profile for all later reads.

**Decision:** Two module-level monotonic tokens (`_profileApplySeq`, `_profileSelectSeq`) implementing "latest switch wins, older in-flight flows abort." `_reloadJournalProfileSelection` bumps `_profileSelectSeq` at entry and re-checks it after every await (blob download, LS fallback, full fetch), returning early before any inject/cache-write if a newer flow took over. `_applyActiveJournalProfile` bumps `_profileApplySeq`; its `finally` now **clears the override to `''` only when still the latest** (settled state carries no pin → reads resolve via active-profile id), and leaves it untouched when superseded (the newer flow owns it) — instead of restoring the transient captured value. Two separate counters because `_applyActiveJournalProfile` awaits `_reloadJournalProfileSelection`; a single shared counter would make the parent read its own child's bump as a supersession. `_injectTrades` gained an optional 4th param `sourceProfileId` (captured pre-await by the caller) so the diagnostic tags the profile that actually produced the data, closing the detection blind spot.

**Consequence:** Concurrent profile switches, rapid double-switches, and Realtime-echo-vs-switch overlaps can no longer cross-contaminate caches or paint the wrong profile's data — the stale flow aborts cleanly at its next post-await checkpoint. Clearing the override to `''` (vs restoring `previousOverride`) is safe because all `_applyActiveJournalProfile` callers invoke it from a top-level unpinned context (verified: profile-select handler, post-create, post-delete), so `''` equals the pre-switch value in the non-raced case while avoiding transient-overlap corruption in the raced case. The `_loadNotionTrades` mutex/re-pin from 2026-05-22 stays as the complementary guard for the full-fetch path. End-to-end confirmation (real Notion M15+H4 profiles + Realtime) is only possible on Max's live setup — but the fixed diagnostic tag means `[ProfileTradeMismatch]` will now actually fire if any residual vector survives. Verified headless: token logic, override lifecycle (stale never clobbers, latest clears), explicit-tag recording, clean boot. Cache JS `?v=1198`.

### 2026-07-04 — Cross-trade screenshot corruption: strict-notionId media match + deterministic self-heal at inject

**Context:** Max reported live that some trade cards render a *different trade's* screenshot in one slot (GBPJPY 12/06 M15-After showing an unrelated USDCAD chart), across several trades. A Full resync **and** a Rebuild screenshots both failed to fix it. Console diagnostics on his real 145-trade dataset were decisive: exactly **3/145** trades corrupted — the 3 most-recent SL trades (GBPJPY 12/06, EURAUD 17/06, GBPNZD 18/06) — **only** the `m15_after` slot, each pointing at a Supabase object `38d8…_m15_after.png` whose embedded notionId is **newer than every trade in the dataset** and matches no live trade = deleted "ghost" trades (pitfall #8: ghosts are never purged from cache). A Supabase HEAD check proved each trade's **own** `<own_notionId>_m15_after.png` object exists (HTTP 200) — so the bytes are fine and correctly uploaded; only the **stored URL string** in the trade data is wrong. Root cause: the positional `media[i]` fallback in `_mergeMediaCache` — when a recent trade's `m15_after` is still a Notion URL (stripped to `''` by `_serializeTradesForStorage` in the LS cache) and its `_notionId` misses a stale sessionStorage media cache, `media[i]` grafts the image sitting at that array index (a ghost trade's `m15_after`); `m15_before` was already a permanent URL in LS so it short-circuits, which is why only one slot corrupts. The poison then propagates into the cross-device raw blob via `_substitutePermanentImageUrls` (reading the poisoned media cache by notionId) → re-infects any fresh device (reproduced on a clean localhost) and **survives resync** because `_preservePermanentImageUrls` keeps the stale permanent URL by notionId.

**Decision:** Two-part fix. **(1) Remove the positional fallback.** `_mergeMediaCache` now matches media strictly by `_notionId` (`byNotionId.get(id) || {}`, never `media[i]`). On a miss the slot is left empty (same trade-off as the raw-blob strip path) rather than showing a wrong-trade image — the next Sync fills it. The two independently-persisted caches (media in sessionStorage, trades in localStorage) drift in order/size, so index `i` in one is never a reliable key into the other. **(2) Deterministic self-heal at the display chokepoint.** New `_healScreenshotOwnership(trades)` runs in `_injectTrades` (the single path all trades pass through into `appState.trades.items`, for every source — cache, sync, blob). For each `/notion-screenshots/<id>_<slot>.png` URL whose `<id>` ≠ the trade's own `_notionId`, it rewrites `<id>` to the trade's own id, preserving the slot and any `?cb=` cache-buster. Chosen over "just tell users to Rebuild" because (a) a plain resync can't fix it (preserve stickiness), (b) Rebuild is a manual per-user action, and (c) the invariant "screenshot URL notionId == trade notionId" holds on 100% of healthy data, so a mismatch is unambiguously corruption and the rewrite target provably exists. The heal is deterministic, idempotent, and a no-op for healthy trades; `*Orig` fields (TradingView/Notion deep-links) and CSV/no-notionId trades don't match the regex and are untouched.

**Consequence:** The corrupted trade card now renders the trade's own image on every load, every device, regardless of what stale caches or the raw blob still hold — so the fix auto-repairs the ~600 community members without any action on their part. The persisted media cache + raw blob may still carry latent ghost URLs, but the inject-time heal masks them permanently (and they self-correct on the next media-queue re-extract). Root cause (`media[i]`) is removed so no new poison can form. Established rule: screenshots are matched by identity only — never by array position — and a deterministic canonical-path invariant (`<notionId>_<slot>.png`) is strong enough to self-heal data corruption at read time. Verified: heal logic tested in isolation (id rewrite, h4_after + query preserved, Orig/CSV untouched, idempotent), `node -c` OK, brace delta 0. **Confirmed fixed live by Max** (hard-refresh localhost → GBPJPY M15-After shows the correct GBPJPY chart).

### 2026-07-04 — Simultaneous Positions v3: band as bidirectional viewport (scroll = single source of truth), win-rate in KPIs (not a 6th widget), static correlation factors

**Context:** A multi-request session extending the (renamed) Simultaneous Positions section raised three design forks. **(a)** The Over Time chart should mirror the horizontally-scrolling Positions Timeline's visible window as a band, and dragging that band should scroll the Timeline back — a two-way binding between a Chart.js canvas and a native scroll container, which risks feedback loops. In Bars mode the band-drag competes with the existing click-a-bar-opens-the-day handler. **(b)** "Win rate by simultaneous positions" (does edge decay as you stack trades?) needed a home — a dedicated 6th widget vs folding into the existing KPIs card. **(c)** The peak-correlation heuristic only clustered by shared currency leg, so index positions (US30 ↔ NAS100) read as uncorrelated, and `_expoPairLegs` even mis-split 6-char index symbols like `NAS100` into `NAS`/`100`.

**Decision:** **(a) The Timeline's `scrollLeft` is the single source of truth.** The band is a pure projection: the Timeline's scroll listener computes the visible fraction `{s,e}` (`_expoUpdateViewportBand`, excluding the sticky gutter) → stores `_expoViewFrac` → redraws the Over Time plugin (`expoViewport`). Line mode additionally jumps-on-press outside the band (no competing click there). The pointerdown listener is bound once to the persistent canvas. **(b) Win-rate folded into the KPIs widget, not a new widget.** Adding a 6th widget to the section means the full ~16-site layout plumbing (`CONCURRENT_POSITIONS_LAYOUT` + all seed spreads + `KIND_BY_ID` + coord reshuffle + hidden-widget/mini-sidebar registry) — high churn, high regression risk for a compact breakdown. **Consequence:** The band is drag-anywhere in both render modes without ever fighting the day-drawer click, and the no-dual-write design means the band and the Gantt can never desync (verified: drag 0.70→0.30 tracked; bars drag suppresses the click while a plain click still opens the day; line jump+track). Correlation now flags index/crypto/energy concentration that was previously invisible. ### 2026-08-12 — Prop Firm Risk Optimizer widget (`w-prop-optimizer`)

**Context:** Max wanted a widget to determine the ideal per-trade risk % to pass a prop-firm challenge, as a function of his win rate, loss streaks, the firm's max drawdown, and the P1/P2 profit targets. The dashboard already has a Monte Carlo widget (`w-montecarlo`) but it is parametric (draws win/loss from a win-rate% + fixed RR) and answers "what does my equity look like over N months" — not "what risk passes".

**Decision:** Build a *distinct* widget, not an extension of the MC one. It is a **barrier Monte Carlo**: for each candidate risk (0.1→3% step 0.1), run 2,000 challenges that **bootstrap-resample the real per-trade R distribution** (`computeEffectiveRR` over the active preset's filtered trades) and race two absorbing barriers — profit target (pass) vs max/daily drawdown (blow). Reuses the MC async MessageChannel chunked engine + compounding/fixed sizing, but the sim loop is new. Lives under the MC widget in section `optimal-rr`; registered in the single `OPTIMAL_RR_LAYOUT` const (+ the 3 TEMPLATE_LAYOUTS blocks) so the `{...OPTIMAL_RR_LAYOUT}` merge auto-injects it for the 600 existing members with zero layout breakage.

Three sub-decisions, each cleared with Max:
1. **Objective = "most aggressive still-safe risk", not raw max pass-probability.** With a positive edge and no time limit, max-pass-probability degenerates to the smallest risk (≈ risk nothing, but 262 trades to pass). The hero number is instead the *highest* risk whose pass probability stays ≥ a user threshold (default 90%, live slider that re-reduces from the stored rows without re-simulating). Fallback to the safest available when no level clears the threshold, flagged `thresholdMet=false`.
2. **Edge source is automatic + editable (Monte Carlo pattern), not a mode toggle.** First cut had a "From my trades / Manual" segmented toggle; Max found it redundant ("there are already the fields to change win rate/expectancy"). Reworked into a single "Your edge" block (win rate / expectancy / trades-per-month) that **auto-fills from the real dataset** and stays synced until the user overrides a field. Untouched + real trades → the sim samples the **full real R distribution** (higher fidelity: real variance/tails). Once any edge field is edited → `_pfEdgeTouched` flips, the sim switches to a **parametric binary model** built from the fields (win avgWin R with prob wr, else −1R; avgWin derived from win-rate + expectancy, loss fixed at −1R), with an explicit status line and a "Reset to my data" link. No journal data → parametric fallback with seeded defaults. No mode button anywhere.
3. **Manual model inputs = win rate + expectancy (+ trades/month), avg win derived.** Matches Max's phrasing ("expectancy important, avg win si besoin") and keeps the model self-consistent (avoids over-determination from typing all of wr/avgWin/expectancy).

**Consequence:** A member gets an actionable "risk this % per trade" that balances speed vs blow-up, backed by their own trade history rather than a generic win-rate+RR formula. The parametric fallback opens the widget to journal-less members and to what-if overrides. Two bugs caught in verification: the summary note used a selector scoped to `#pf-cards` (note lived outside it), and the "Reset to my data" link stayed visible because `all: unset` reset `display`, defeating the `hidden` attribute (fixed with `.pf-edge-reset[hidden]{display:none}`). Real interior optimum (via a trade/time budget, min-days, consistency rule) and configurable avg loss / direct avg-win input are logged as a Deferred follow-up. `node -c` OK, brace delta 0, caches JS `?v=1418` / CSS `?v=397`. To be validated live by Max on his real Notion data.
